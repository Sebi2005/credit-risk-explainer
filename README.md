# Credit Risk Explainer

A Python application that estimates the probability of serious delinquency within two years, explains individual Random Forest predictions with SHAP, and displays the results in Streamlit.

The project combines an evaluated tabular ML pipeline with exact applicant lookup, missing-value handling, and an optional local LLM integration whose structured output is checked against the computed evidence.

## Features

- Applicant lookup by a stable ID, independent of row order.
- Random Forest probabilities with a validation-selected classification threshold.
- The same predictions used for individual lookup and applicant searches.
- Observed values displayed directly by Python; missing values remain explicitly unknown.
- SHAP tables and charts, including missing-value indicator contributions.
- A reconstruction check: SHAP baseline plus all contributions must match the predicted probability.
- Separate manual indicators and suggestions, with cautious debt-ratio interpretation when income is missing.
- Optional LM Studio structured-output integration with validation and a deterministic fallback.
- Small offline tests that require neither Streamlit nor a running LLM server.

## Architecture

| File | Responsibility |
|---|---|
| `app.py` | Streamlit inputs, tables, charts, status messages and errors |
| `risk_service.py` | Dataset/model loading, lookup, batch scoring, search, manual rules and SHAP |
| `explanations.py` | Evidence preparation, JSON parsing, validation, local LLM call and sentence rendering |
| `tests/test_core.py` | Minimal offline regression tests using a small synthetic model |
| `Model_Training.ipynb` | Existing training notebook: splits, model comparison, threshold selection, evaluation and artifact export |
| `requirements.txt` | Runtime dependency names; not a version lockfile |

The logic modules contain no Streamlit calls. `RiskService` caches the dataset, scored table, saved model and explainer in memory; Streamlit caches the service instance. Restart the app after replacing the CSV or model artifact.

### Individual explanation flow

1. Resolve the applicant ID and select the original CSV row.
2. Pass the original feature values to the saved pipeline in its expected column order.
3. Impute missing values with training medians and create missing-value indicators.
4. Obtain the probability of target class `1` and compare it with the saved threshold.
5. Explain the forest on its transformed input using Tree SHAP.
6. Verify reconstruction and display all contributions in percentage points.
7. Optionally send the five largest non-negligible contribution directions to LM Studio.
8. Validate the returned JSON and render sentences in Python. Use the same factual template if the server is unavailable or the response is invalid.

### Role of the LLM

The current local model is `deepseek-r1-distill-qwen-1.5b`, served by LM Studio at `http://127.0.0.1:1234/v1`.

The LLM does **not** predict risk, compute SHAP, or independently write the displayed explanation. It returns a constrained representation of evidence already supplied by Python. The validator checks the risk label, exact feature coverage, contribution directions, missing-feature information, duplicates and unexpected fields. Python controls the final sentences.

Successful LLM validation and fallback therefore produce equivalent factual wording. This optional integration demonstrates structured-output validation and fallback handling, but currently adds little functionality beyond the deterministic explanation. It is not an autonomous agent or a RAG system. Earlier FAISS applicant retrieval was removed from the main flow because other profiles do not explain an individual prediction and contaminated generated text.

## Dataset and target

The project uses the [Give Me Some Credit](https://www.kaggle.com/c/GiveMeSomeCredit) training dataset, `cs-training.csv`.

- 150,000 labeled rows.
- 10 predictor columns; the applicant identifier is excluded from training.
- Target: `SeriousDlqin2yrs`, indicating serious delinquency of 90 or more days within two years.
- Positive-outcome prevalence: approximately 6.68%.

The unnamed first CSV column is preserved as `applicant_id`. The recorded target is not the model prediction: an applicant with recorded outcome `0` may receive a High prediction (a false positive when compared with that outcome).

The application reads the **original CSV**, not the CSV generated by the earlier preprocessing/FAISS notebook. Observed values, including extremes, remain visible. Missing income can make the debt-ratio interpretation uncertain; the app flags that situation instead of automatically issuing a debt-ratio suggestion.

Obtain the dataset according to the source's access conditions. It and the user's trained `.joblib` file are not included in this refactoring package.

## Training and model selection

The existing `Model_Training.ipynb` uses reproducible stratified splits with `random_state=42`:

| Set | Rows | Share |
|---|---:|---:|
| Training | 90,000 | 60% |
| Validation | 30,000 | 20% |
| Test | 30,000 | 20% |

Preprocessing statistics are learned only from training data. The baseline logistic regression uses median imputation, missing indicators and standard scaling. The selected forest uses median imputation and missing indicators, without scaling.

Random Forest settings:

```python
RandomForestClassifier(
    n_estimators=200,
    max_depth=12,
    min_samples_leaf=20,
    random_state=42,
    n_jobs=-1
)
```

No class weighting was configured. This project does not claim the model or threshold is globally optimal.

### Validation comparison

| Metric | Logistic regression | Random Forest |
|---|---:|---:|
| ROC-AUC | 0.6918 | 0.8657 |
| Average precision | 0.2267 | 0.3870 |

Among candidate thresholds `0.05, 0.10, 0.15, 0.20, 0.25, 0.30, 0.40, 0.50`, **0.25** had the highest validation F1 (approximately 0.437). The nearby 0.20 threshold scored approximately 0.435. F1 was a demonstration criterion, not an estimated lending-cost function.

### Held-out test results

These results were obtained in the original training notebook before this refactor; the original artifact and dataset were not supplied for independent rerunning during refactoring.

| Metric | Random Forest, threshold 0.25 |
|---|---:|
| ROC-AUC | 0.8676 |
| Average precision | 0.4025 |
| Positive-class precision | 0.429 |
| Positive-class recall | 0.453 |
| Positive-class F1 | 0.441 |
| Accuracy | 0.923 |

| Actual outcome | Predicted 0 | Predicted 1 |
|---|---:|---:|
| 0 | 26,788 | 1,207 |
| 1 | 1,097 | 908 |

Always predicting `0` would achieve approximately 93.32% accuracy while detecting no positive outcomes. Accuracy alone is therefore not the selection criterion.

Average precision summarizes precision–recall performance and is not classification accuracy or the trapezoidal area under a precision–recall curve.

## Setup

### Use with the existing project

Copy `app.py`, `risk_service.py`, `explanations.py`, `requirements.txt`, `README.md`, and `tests/` into the project's main folder. Back up the old `app.py` first. Keep the existing training notebook, original CSV and saved model in place:

```text
MLProject/
    app.py
    risk_service.py
    explanations.py
    requirements.txt
    README.md
    Model_Training.ipynb
    dataset/
        cs-training.csv
    models/
        credit_risk_model.joblib
    tests/
        test_core.py
```

The model bundle must contain `pipeline`, `threshold`, and `feature_columns`. The pipeline steps must be named `imputer` and `classifier`, as in the existing notebook. The classifier must contain class `1`.

### Python environment

Prefer the existing virtual environment used for training:

```powershell
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

The dependency list is intentionally unpinned because the exact user's training versions were not supplied. Preserve the training environment's scikit-learn version when loading its serialized model. Inspect the bundle's `sklearn_version` if available and avoid blindly upgrading the training environment. Model persistence is not guaranteed across library versions.

Once the app works locally, record the exact environment for reproducibility:

```powershell
python -m pip freeze > requirements-lock.txt
```

Only load trusted `.joblib` artifacts: deserialization can execute code.

### LM Studio

1. Load `deepseek-r1-distill-qwen-1.5b` in LM Studio.
2. Start the local API server on port `1234`.
3. If the served model identifier differs, edit the `ChatOpenAI` configuration in `explanations.py`.

No OpenAI API key or `.env` file is required for this local configuration. The app still displays predictions, SHAP and a template explanation if the local server is unavailable; the request may wait until its timeout first.

### Run

From the project folder:

```powershell
python -m streamlit run app.py
```

Open the displayed local URL, usually `http://localhost:8501`.

If the previously observed Streamlit watcher/Transformers inspection messages reappear, disable file watching:

```powershell
python -m streamlit run app.py --server.fileWatcherType none
```

With file watching disabled, restart Streamlit after editing code. Stop with `Ctrl+C`.

### Examples

```text
1
Why was applicant 1 flagged as high risk?
Explain applicant 7
Show high risk applicants
Show low risk applicants
Show applicants with high credit utilization
Show applicants with delinquency
```

Search supports explicit phrases, not unrestricted natural-language query understanding. It applies the first matching condition and returns the first three matches in dataset order; these are not the three highest probabilities. High utilization means above the manual 35% threshold and can include applicants predicted Low. Conditions are not combined. A standalone number or an explicit `applicant [ID]` phrase selects an individual.

For the previously checked artifact, applicant 1 has probability approximately 32.81% (High), applicant 2 approximately 9.19% (Low), and applicant 7 approximately 3.35% (Low, income missing). Different artifacts can produce different results.

## Minimal tests

Run from the project folder:

```powershell
python -m unittest discover -s tests -v
```

Six test methods cover:

- Plain, fenced and wrapped JSON; duplicate-key rejection.
- Six incorrect evidence mutations: label, direction, duplicate/omitted factors, missingness and an extra claim.
- A simulated successful LLM response and server-unavailable fallback.
- Search/lookup agreement and SHAP reconstruction on a small synthetic forest.
- Missing-income preservation, reconstruction and invalid IDs.
- Query routing and the debt-ratio rule when income is unavailable.

Tests use temporary synthetic data and a small locally trained model. They do not call LM Studio, open Streamlit, or require the production CSV/model. They validate behavior, not the performance metrics of the original trained artifact. There is no broad measured evaluation of live LLM acceptance or fallback rates yet.

## Limitations

- Educational demonstration, not a production lending decision system; no compliance or fairness certification is claimed.
- A High label means probability at or above 25%, not necessarily greater than 50%. Low does not mean zero risk.
- Output probabilities have not been explicitly calibrated or assessed with a calibration study.
- A random held-out split measures generalization within this dataset, not temporal or external-population performance.
- Some displayed applicants may belong to the training split. Individual app examples are not held-out performance evidence.
- SHAP uses `tree_path_dependent` TreeExplainer. Attributions depend on the model and explainer assumptions, especially for related features; they are not causal effects or guarantees of what changing a feature would do.
- Missing income is displayed as unknown even though the model explains a median-imputed value. The missing indicator has its own contribution.
- Rule thresholds and suggestions are illustrative, separate from SHAP, and do not guarantee a lower prediction or approval.
- The optional LLM copies constrained evidence; Python renders the final explanation. This is intentionally limited and must not be described as free-form validated financial reasoning.
- Supporting tests and two live examples do not establish universal LLM reliability.

## Project history

The original lab prototype combined manual risk rules, applicant-description embeddings, FAISS retrieval and a local LLM. The revised app adds model training/evaluation, consistent model-backed searches, SHAP and structured validation, and removes applicant-profile retrieval from the core flow. Earlier RFC/diagram files describe the original architecture and should be updated or marked historical before publication.
